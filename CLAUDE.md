# Expense Tracker — CLAUDE.md

This file orients Claude Code (and any other agent) working in this repo. It
is deliberately specific to what actually exists here — update it in the same
commit whenever architecture, conventions, or commands change underneath it.

## What this is

A small full-stack expense tracker: add an expense (description, amount,
category, date), see the list, see a running total, delete entries. It's
intentionally minimal — the point is a clean, correct foundation, not feature
breadth. Resist the urge to add auth, multi-user support, budgets, or
recurring expenses unless explicitly asked; extend the schema and routes
below rather than bolting on parallel structures.

## Data model and money handling

`Expense.amountCents` is an **integer number of cents**, not a float dollar
amount. This is the one convention in this codebase that must never be
violated:

- Forms and API input use `amountDollars` (a decimal the user typed).
- `dollarsToCents` / `centsToDollars` / `formatCents` in `src/lib/money.ts`
  are the only places that convert between the two. Don't do `amount * 100`
  inline elsewhere — route it through these helpers so rounding stays
  consistent (see the `dollarsToCents(19.99)` test for why this matters:
  naive float math gives `1998.999...`, not `1999`).
- The database and all internal arithmetic (sums, totals) stay in cents.
  Only convert to dollars at the point of display.

`Category` is a Prisma enum (`FOOD`, `TRANSPORT`, `HOUSING`, `UTILITIES`,
`ENTERTAINMENT`, `HEALTH`, `OTHER`), mirrored as a const array in
`src/lib/validations.ts` (`CATEGORIES`) so the client can render options
without importing generated Prisma code into a Client Component. If you add a
category, update both and regenerate the client (`npx prisma generate`).

## API conventions

- Routes live under `src/app/api/**/route.ts` and validate all input with the
  Zod schemas in `lib/validations.ts` before touching Prisma. A `safeParse`
  failure returns `400` with `error: parsed.error.flatten()` — keep that
  shape consistent if you add routes, since the form's error handling expects
  it.
- Routes return plain JSON matching `ExpenseDTO` (`lib/types.ts`), not raw
  Prisma model instances — `occurredOn` is serialized to an ISO string.
  If you add a field to the schema that needs to reach the client, add it to
  `ExpenseDTO` too; don't assume Prisma's shape and the wire shape are the
  same forever.
- Dynamic route params are async (`{ params }: { params: Promise<{ id: string
  }> }`) — this is Next 15+/16 behavior, not a mistake; don't "simplify" it
  back to a synchronous destructure.

## Database workflow

- `prisma/schema.prisma` is the source of truth. Change it, then run
  `npm run db:migrate` — never hand-edit `dev.db` or files under
  `prisma/migrations/`.
- Migrations are committed. If your change conflicts with a teammate's
  migration, regenerate rather than editing history.
- `dev.db` itself is gitignored (`*.db`, `*.db-journal`) — every environment
  builds its own from migrations. Don't rely on data in it persisting, and
  don't commit it.
- Config lives in `prisma7.config.ts` (Prisma 7's config file, not the old
  `package.json#prisma` block), and reads `DATABASE_URL` from `.env` (see
  `.env.example` — copy it to `.env` locally; `.env` itself is gitignored).

### Prisma 7 specifics worth knowing before you "fix" something

- The generator is `prisma-client` (the new TS client), not the old
  `prisma-client-js`. Its output has no `index.ts` — import from
  `@/generated/prisma/client`, not `@/generated/prisma`.
- `PrismaClient` now requires an explicit driver adapter; there is no bundled
  query engine binary fallback for SQLite anymore. `src/lib/prisma.ts`
  constructs one from `@prisma/adapter-better-sqlite3`. If you switch
  databases (e.g. to Postgres for production), swap the adapter package and
  the `datasource` provider in `schema.prisma` together — they must agree.
- `npx prisma init` also installed agent-facing reference docs under
  `.claude/skills/`, `.agents/skills/`, and `.windsurf/skills/`
  (`prisma-client-api`, `prisma-cli`), tracked by `skills-lock.json`. These
  are real Prisma-maintained docs, not scaffolding cruft — check them before
  guessing at Prisma API shape from older training data, since the client API
  here differs from Prisma 5/6.

## Testing

- Unit tests live next to what they test in `__tests__/` directories and run
  under Vitest with jsdom. `src/lib/__tests__/money.test.ts` is the pattern
  to follow for pure-function tests.
- There is no API/integration test harness yet (no test database, no request
  mocking setup). If you add one, prefer a separate SQLite file
  (`file:./test.db`) over mocking Prisma, and gitignore it the same way as
  `dev.db`.
- No end-to-end browser tests yet. Before claiming a UI change works, run
  `npm run dev` and exercise it manually (add an expense, delete it, confirm
  the total updates) — `typecheck`/`lint`/`test` passing is not the same as
  the feature working.

## Conventions

- Money: see "Data model and money handling" above — always cents internally.
- Validation: one Zod schema per input shape in `lib/validations.ts`, reused
  by both the API route and (if you add client-side validation) the form.
  Don't duplicate validation rules inline.
- Components: Server Components by default; add `"use client"` only where
  there's actual interactivity (state, event handlers, browser APIs).
  `page.tsx` fetches via Prisma directly (it's a Server Component) — don't
  route it through `fetch("/api/expenses")`, that's only for the client.
- No comments explaining *what* code does — names should carry that. The
  existing comments in this repo (e.g. the money-cents note, the async
  `params` note above) exist because the reasoning is non-obvious or
  contradicts common defaults; match that bar, not "explain every function."
- Formatting is Prettier's defaults (`npm run format`); don't hand-tune
  spacing that Prettier would just rewrite.

## Environment variables

| Variable        | Purpose                              | Default (`.env.example`) |
|------------------|----------------------------------------|-----------------------------|
| `DATABASE_URL`    | SQLite file path for Prisma            | `file:./dev.db`               |

`.env` is gitignored. Never commit real credentials here — for this project
there currently are none (SQLite needs no secret), but if a future change
adds an external service, put its key in `.env`/`.env.example` (placeholder
value) following this same pattern, not hardcoded in source.

## Known gaps / explicitly out of scope for now

- No authentication — this is a single-user local tool as it stands. Don't
  add auth speculatively; if asked, it's a real design decision (sessions?
  who owns an expense?) that deserves its own discussion, not a quick bolt-on.
- No pagination on the expense list — fine at prototype scale, will need
  addressing if this becomes a real multi-year ledger.
- No edit-in-place for an existing expense (only create/delete). Adding it
  means a `PATCH /api/expenses/[id]` route plus a form mode toggle — follow
  the existing POST/DELETE routes as the template.
